# 質問バンク

①〜③で使う質問の候補。**全部聞くためのリストではない。** プロジェクトの種類（Web アプリ／CLI／ライブラリ／データ分析／ドキュメント／個人ツール）に応じて 3〜4 問ずつ選び、回答を見て次のラウンドを決める。

各質問に「なぜ聞くか」を添えている。質問文をそのまま読み上げるより、意図を汲んでユーザーの文脈に合わせて言い換える方がよい。

---

## §1 要件

### 1-1 目的・ユーザー

| 質問 | なぜ聞くか |
|---|---|
| 一言で言うと何を作る？ 誰が使う？ | スコープの核。ここが曖昧なら以降が全部ブレる |
| そのユーザーは今、その課題をどう解決している？ | 既存手段との差分が価値。「特にない」なら課題自体を疑う材料になる |
| これができたら、ユーザーの何が変わる？ | 成功の定義につながる。機能ではなく結果で語らせる |
| 自分用か、他人に使わせるか、売るか | 品質・UX・セキュリティ・ドキュメントの要求水準が桁で変わる |

### 1-2 スコープ

| 質問 | なぜ聞くか |
|---|---|
| 最初のリリースで **絶対に** 必要な機能を 3 つ以内で | MVP の輪郭。3 つに絞れないなら優先順位が未整理 |
| 逆に、今回は **やらない** と決めていることは？ | 「やらないこと」が空だとスコープが際限なく膨らむ。最低 1 つは引き出す |
| 将来やりたいが今回は見送るものは？ | 拡張性をどこまで設計に織り込むかの判断材料 |

### 1-3 成功基準・制約

| 質問 | なぜ聞くか |
|---|---|
| 「できた」と判断する基準は？ 測れる形で言えるか | 完成条件が曖昧だと終わらない。数値・具体的シナリオに落とす |
| 期限やマイルストーンは？ | スコープと構成の複雑さの上限を決める |
| 既存システム・データ・API と繋ぐ必要があるか | 統合点は要件・構成・MCP 選定の全部に影響する |
| 使わなければならない／使ってはいけない技術は？ | 会社方針・ライセンス・スキルセットによる制約 |
| チームは何人？ Claude 以外の開発者はいる？ | 規約の厳しさ、ドキュメントの量、レビュー体制を決める |

### 1-4 非機能要件

全部は聞かない。プロジェクト種別から明らかに無関係なものは飛ばす。

| 領域 | 聞き方の例 |
|---|---|
| 性能 | 同時利用者数、データ量、許容レスポンス |
| セキュリティ | 個人情報・決済・認証を扱うか。公開サーバーか |
| 可用性・運用 | 止まったら困る度合い。誰が運用するか。監視は要るか |
| データ | 消えたら困るデータはあるか。バックアップ、移行 |
| 対応環境 | OS、ブラウザ、モバイル、オフライン |
| i18n / a11y | 多言語、アクセシビリティの要件 |
| 法規・コンプライアンス | 業界規制、利用規約、ライセンス |

### 1-5 リスク・未決

| 質問 | なぜ聞くか |
|---|---|
| 一番不安な点、うまくいかなそうな点は？ | ユーザー自身が感じているリスクは最優先で要件定義書に載せる |
| まだ決めていない・決められないことは？ | 未決事項を明示しておくと、後で「決めたつもり」の齟齬が防げる |

## §2 フォルダ構成

### 2-1 技術スタック

| 質問 | なぜ聞くか |
|---|---|
| 言語とバージョン、フレームワーク | ツリーの骨格を決める。フレームワークに標準構成があるならそれに従うのが基本 |
| パッケージマネージャ、ビルド／テスト／リンター | CLAUDE.md のコマンド節と `.claude/settings.json` の許可リストに直結 |
| DB / ストレージ / 外部サービス | `infra/`、`migrations/`、MCP 候補に影響 |

### 2-2 構造の決め

| 質問 | 選択肢の例 | なぜ聞くか |
|---|---|---|
| 単一パッケージかモノレポか | 単一 / モノレポ（apps+packages） | 規模とチーム構成による。モノレポは小規模だと過剰 |
| コードの分け方 | 機能別（feature-based） / 種類別（controllers, models…） / ドメイン層あり | 中規模以上は機能別が保守しやすいが、フレームワーク標準があるなら従う |
| テストの置き場所 | ソース隣（コロケーション） / `tests/` に分離 | 言語コミュニティの慣習に合わせるのが無難 |
| ドキュメントの置き場所 | `docs/` / README のみ / Wiki 等外部 | 要件定義書と ADR をどこに置くかが決まる |
| スクリプト・ツール類 | `scripts/` / `tools/` / Makefile / タスクランナー | CLAUDE.md の「よく使うコマンド」の実体 |

### 2-3 参照・規約

| 質問 | なぜ聞くか |
|---|---|
| 参考にしたいリポジトリやテンプレートはあるか | あるならそれを読んで構成を寄せる。ゼロから議論しない |
| 社内・チームの既存規約はあるか | 構成の自由度がどれだけあるかを知る |

### 2-4 暫定ツリーの提示

回答を得たら、次の形で提示して認識を合わせる（確定ではない）：

```
project/
├── CLAUDE.md
├── README.md
├── docs/
│   └── requirements.md
├── src/
│   └── ...
├── tests/
└── .claude/
    ├── settings.json
    ├── skills/
    └── agents/
```

ツリーには **なぜその分け方にしたか** を 1〜2 行添える。ユーザーが判断できる材料を与える。

## §3 CLAUDE.md

前提として共有すること：CLAUDE.md は毎セッションの先頭で読まれる。だから **短いほど効き、Claude が知らないことだけを書くほど効く**。言語の一般常識、フレームワークの公式ドキュメントに書いてあること、リンターが検出することは書かない。

### 3-1 コマンド

| 質問 | なぜ聞くか |
|---|---|
| ビルド・テスト・リント・開発サーバー起動・デプロイのコマンドは？ | Claude が最初に迷うのはここ。正確なコマンドがあると試行錯誤が消える |
| 実行してはいけない・確認なしに実行してほしくないコマンドは？ | `settings.json` の deny / ask に落とす。CLAUDE.md にも一言 |
| 環境変数・シークレットの扱い | `.env` の存在、何が必要か、どこから取るか |

### 3-2 規約・アーキテクチャ

| 質問 | なぜ聞くか |
|---|---|
| リンターで検出できないコーディング規約は？（命名の意図、エラーハンドリング方針、ログの書き方） | 機械検出できるものは書かなくてよい。人間の判断が要るものだけ |
| 触ってほしくない層・ファイル、依存の向きの制約 | アーキテクチャの境界を Claude は推測できない |
| ドメイン用語で、一般語と意味がズレるもの | 「ユーザー」が誰を指すか等。誤解が要件の誤実装に直結する |
| 設計上の決定で、理由を残しておきたいもの | ADR に切り出す候補。CLAUDE.md からは参照だけにする |

### 3-3 Git・チーム運用

| 質問 | なぜ聞くか |
|---|---|
| ブランチ命名、コミットメッセージ形式、PR の作法 | チーム運用がある場合のみ。個人開発なら軽く |
| コミット・プッシュを Claude に任せるか、確認を挟むか | 権限設計に直結 |

### 3-4 Claude への期待

| 質問 | なぜ聞くか |
|---|---|
| 応答言語、説明の粒度（要点だけ / 丁寧に） | ユーザーの好みは推測より明示が確実 |
| 確認を取ってから進めてほしい操作 | 破壊的変更、外部 API 呼び出し、課金が発生する操作など |
| テストを先に書くか、後に書くか、書かないか | 開発スタイルの前提 |
| 分からないとき、勝手に決めてよいか、聞いてほしいか | 自律性の度合い |
| 作業をタスク単位で頼むか（「この関数を直せ」）、ゴール単位で任せるか（「この機能を動くようにせよ」） | 指示の粒度が CLAUDE.md の「Claude への期待」と権限設計を決める。ゴール単位なら、Claude が自分で「動いた」と確かめる手段が要る |
| 途中経過を見たいか、結果だけ見たいか | 結果だけ見たいなら、代わりに検証とレビューの仕組み（§3-5）が要る。人の目が減った分を仕組みで埋めないと、任せた範囲がそのまま品質の穴になる |

### 3-5 検証・レビュー・フィードバックの 3 ループ

Claude Code チーム自身の開発スタイルから借りた考え方。Claude に任せる範囲を広げるほど、**「動いたことを確かめる」「変更を見直す」「使った人の反応を拾う」** の 3 つのループが品質を支える。この 3 つは **必ず聞く**。答えが「まだない」でもよいが、その場合は「ない」と要件定義書の未決事項に残す。

| ループ | 質問 | なぜ聞くか |
|---|---|---|
| 検証 | 変更が「動いた」と何で確かめるか（テスト、型チェック、リント、開発サーバーを起動して操作、スクリーンショット、ログ）。それを Claude が自分で回せるか | CLAUDE.md の「完了の定義（検証）」節になる。Claude が自力で検証できないなら、ゴール単位で任せることはできない |
| レビュー | 誰が／何が変更を見直すか（人、CI、読み取り専用の reviewer agent）。PR 前に必ず通すチェックは何か | 「PR 前チェック」を skill にする根拠。人がレビューしないなら、代わりに何が見るのかを明示しないと誰も見ていない状態になる |
| フィードバック | 使った人の声・障害・要望をどこから拾うか（Issue、Slack、ログ、アナリティクス、自分で使う）。どの頻度で巡回するか | 「フィードバック巡回」を skill にする根拠。拾う場所が決まれば MCP 候補（Slack、Issue トラッカー）も決まる |

**ファンアウト → 反証レビュー**（観点別の複数エージェントで指摘を出し、別エージェントが「本当に問題か」を反証する構成）は、**ここでユーザーが明示的に求めたときだけ** 作る。こちらから提案しない。理由: エージェントが増えるほどコストと保守が増え、単一の reviewer で足りるプロジェクトが大半だから。求められた場合のテンプレートは `scaffold-guide.md` §5。

### 3-6 分割の判断

| 質問 | なぜ聞くか |
|---|---|
| 特定のディレクトリ・ファイル種別にだけ効くルールはあるか（フロントだけ、テストだけ、マイグレーションだけ） | `.claude/rules/<topic>.md` に `paths:` を付けて分離すると、CLAUDE.md 本体を短く保てる |

### 3-7 除外の提案

回答の中に次のようなものがあれば、その場で「CLAUDE.md には書かなくてよい」と理由を添えて提案する：

- 言語・フレームワークの標準的な使い方（公式ドキュメントで足りる）
- リンター／フォーマッターが強制している規約（`.eslintrc` 等が真実）
- 一度しか使わない手順（skill にするか、`docs/` に置く）
- 長い背景説明（要件定義書に置き、CLAUDE.md には要点のみ）
- 今のモデル・ツールの限界に合わせた回避策（「〜は苦手なので毎回〜する」「このツールは使わない」）。恒久ルールにしない。書くなら `<!-- 賞味期限: YYYY-MM -->` を付け、モデルやツールが更新されたら消す
