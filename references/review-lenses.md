# レビューレンズ — クリティカルシンキング × ラテラルシンキング

④で①〜③の回答に当てるレンズ。**クリティカル** は「今ある案の穴を見つける」、**ラテラル** は「別の案があり得ないか探す」。両方やる。片方だけだと、穴のない凡庸な案（クリティカルのみ）か、面白いが破綻した案（ラテラルのみ）になる。

指摘は **「指摘 → 根拠 → 提案」** の 3 点セットで書く。根拠のない指摘は感想であり、提案のない指摘は愚痴だ。

---

## A. クリティカルシンキング（守り）

### A-1 前提の検証
- ユーザーが「当然」として語ったことのうち、確認されていないものはどれか。
- 「ユーザーはこう使うはず」「この技術が最適なはず」の *はず* を列挙し、根拠の有無を問う。
- 問い：「もしこの前提が間違っていたら、どの決定が崩れるか？」崩れる範囲が大きい前提ほど早く検証すべき。

### A-2 整合性
- ①要件 ↔ ②構成：構成が要件に対して過剰／不足していないか（3 画面のツールにマイクロサービス、等）。
- ①要件 ↔ ③CLAUDE.md：要件で「重要」と言った非機能要件が CLAUDE.md に一言もない、等。
- ②構成 ↔ ③CLAUDE.md：CLAUDE.md が言及するディレクトリ・コマンドが構成に存在するか。
- 回答同士の矛盾：「個人用」と言いつつ「多言語対応」など。矛盾は片方が本音でないサイン。

### A-3 抜け・盲点
- 非機能要件で触れられなかった領域（`questions.md` §1-4 の表と突き合わせる）。
- ライフサイクルの抜け：作った後の運用、データ移行、廃止、エラー時の挙動、初回セットアップ。
- ステークホルダーの抜け：使う人以外に、困る人・承認する人・運用する人はいないか。
- 「やらないこと」が空欄か薄い。

### A-4 測定可能性
- 成功基準は第三者が判定できるか。「使いやすい」「速い」は数値か具体的シナリオに落とす。
- 完成条件が「機能一覧が全部できたら」になっていないか。それは完成の定義ではなく作業一覧だ。

### A-5 YAGNI・複雑性
- 今回のスコープに必要ない抽象化・層・設定はないか。
- 「将来のために」入っているものを列挙し、それぞれ「今入れないと後で何が困るか」を問う。困らないなら外す。
- 構成のディレクトリで、最初のリリース時点で空のままになりそうなものは？

### A-6 実現可能性・リスク
- 期限・人数・スキルに対してスコープは現実的か。
- 外部依存（API、ライブラリ、サービス）で、止まったら／仕様変更されたら詰むものは？
- ユーザーが「一番不安」と言った点は、要件・構成のどこで手当てされているか。されていなければ最優先の指摘。

### A-7 CLAUDE.md 固有
- Claude が公式ドキュメントから知れることが書かれていないか（削る）。
- 抽象的な精神論（「きれいなコードを書く」）になっていないか（具体的な判断基準に置き換えるか削る）。
- 100〜200 行に収まるか。収まらないなら何を `.claude/rules/` に逃がすか。
- 「〜しないこと」の禁止事項に理由がついているか。理由がないと Claude は例外判断ができない。
- **賞味期限**: 今のモデル・ツールの限界に合わせた回避策（「大きなファイルは分割して読ませる」「〜は苦手なので毎回確認」）や、特定ツールへの執着が、恒久ルールとして書かれていないか。書くなら `<!-- 賞味期限: YYYY-MM -->` を付けて見直し時期を決める。モデルが更新されれば不要になる指示は、不要になったときに消せる形にしておく。
- **3 ループの有無**: 検証（何で「動いた」と確かめるか）・レビュー（誰が／何が見直すか）・フィードバック（使った人の声をどこから拾うか）が CLAUDE.md の目次に一つもなければ指摘する。Claude に任せる範囲に対して、確かめる手段が釣り合っているか。

## B. ラテラルシンキング（攻め）

各技法を **少なくとも一つは試す**。出た案が全部却下されても構わない。却下された案は要件定義書の「検討したが採用しなかった選択肢」に残す。

### B-1 逆転
- 要件を逆にしたら？（「入力を楽にする」→「入力をなくす」）
- 順番を逆にしたら？（「作ってから使ってもらう」→「使ってもらいながら作る」）
- 誰がやるかを逆にしたら？（ユーザーが手で分類 → システムが提案してユーザーが承認）
- 開発の役割を逆にしたら？（人が書いて Claude がレビュー → Claude が書いて Claude 群が観点別にレビューし、人は設計判断だけをする）。これは **問いであって構成の提案ではない**。ファンアウト構成（複数 reviewer agents）は、ユーザーが自ら求めたときだけ作る（`scaffold-guide.md` §5）。

### B-2 極端化
- ユーザーが 1 人だったら／100 万人だったら、何を削れる／何が必要になるか。
- 予算・期限がゼロだったら何を残すか → それが本当の MVP。
- 全部手動でやったら？ → 自動化の価値がある部分だけが見える。

### B-3 他分野からの転用
- この課題と構造が似ている別分野の解決策は？（在庫管理 ↔ タスク管理、レコメンド ↔ 検索、等）
- ゲーム、飲食店、図書館、郵便、医療など、まったく違う業界ならどう解くか。
- 過去のプロジェクトで似た問題をどう解いたか、ユーザーに聞く。
- Claude Code チームの開発スタイルからの転用：「作る」でなく **「Claude に繰り返し実行させる」** で済む要件はないか（毎週のレポート生成を機能として実装する → skill にして Claude に実行させる）。仕組みをコードで固定する前に、運用で回してみる。

### B-4 制約の操作
- 制約を一つ外したら設計はどう変わるか。その制約は本物か、思い込みか。
- 逆に制約を一つ足したら（「DB を使わない」「画面を一つにする」「1 週間で作る」）、何が本質として残るか。

### B-5 組み合わせ・流用
- 既存のサービス・OSS・ノーコードツールを組み合わせて **作らずに** 済ませられないか。
- 要件のうち 2 つを一つの機能で満たせないか。
- 既存プロジェクトの資産（コード、データ、ドキュメント）で流用できるものは？

### B-6 視点の切り替え
- 初めて使う人、毎日使う人、やめる人、運用する人、それぞれから見て要件はどう見えるか。
- 1 年後の自分がこのプロジェクトを開いたとき、何があれば助かるか → CLAUDE.md と docs に効く。
- 競合や先行事例があるなら、彼らが「あえてやっていないこと」は何か。

### B-7 ランダム刺激（最後の手段）
- 出た指摘が凡庸なとき、無関係な単語（例：「天気」「駅」「弁当」）を一つ選んで要件と強引に結びつける。9 割はゴミだが 1 割は使える。

## C. レビューレポートの形式

このテンプレートで提示する。**採用／不採用／保留をユーザーが指摘単位で選べる** ことが重要なので、指摘には番号を振る。

```markdown
# レビューレポート

## 全体所見
（2〜4 行。最も大きな懸念と、最も有望な別解を一つずつ）

## 指摘一覧

| # | 対象 | レンズ | 指摘 | 根拠 | 提案 |
|---|------|--------|------|------|------|
| 1 | ①要件 | A-4 測定可能性 | 成功基準「使いやすい」が判定不能 | 完成判定を第三者ができない | 「新規ユーザーが説明なしに 3 分以内で初回登録を完了」に置換 |
| 2 | ②構成 | A-5 YAGNI | `packages/shared` が初期リリースで空になる | 共有コードが現時点で存在しない | 単一パッケージで開始し、共有が 2 箇所以上で発生した時点で切り出す |
| 3 | ①要件 | B-5 組み合わせ | 認証を自作する必要がない | 要件はメール認証のみ、規制要件なし | 既存の認証サービスの採用を検討 |
| … | | | | | |

## 改訂後の要件サマリー
（採用前提の暫定版。①の 6 項目を各 1〜3 行で）

## 改訂後のフォルダ構成
（ツリー。変更点にコメント）

## CLAUDE.md の目次案
（節見出しと、各節に何を書くか 1 行ずつ。`.claude/rules/` に分ける項目があれば明記）

## 未決事項
（決めなくても進められるが、いつまでに決めるべきかを添える）
```

提示後、指摘ごとに採用／不採用／保留を聞く。AskUserQuestion が使えるなら multiSelect で「採用する指摘」を選ばせるのが速い。

全件の判断が出たら、**確定版** を短く提示して⑤へ：

```markdown
# 確定版

## 採用した指摘
（番号と一行要約）

## 検討したが採用しなかった選択肢
| 選択肢 | 却下理由 | 再検討の条件 |
（不採用・保留になった指摘から。要件定義書 §9 へ転記する）

## 最終の要件サマリー / フォルダ構成 / CLAUDE.md 目次
（採用を反映した版。変更がなければ「レビューレポートの通り」と書くだけでよい）
```

## D. レビューの質を自己点検する

提示前に以下を確認する。一つでも No なら該当レンズを当て直す。

- 「削る／後回しにする／作らない」方向の提案が **1 つ以上** あるか。
- ユーザーが「一番不安」と言った点に触れているか。
- 指摘のうち、採用されたら **決定が変わる** ものが半分以上か（言い回しの修正ばかりになっていないか）。
- ラテラル系の提案が **1 つ以上** あるか。
- CLAUDE.md の目次案に、検証・レビュー・フィードバックの 3 ループが載っているか（③で一つも聞けていなければ、⑤に進む前に③へ戻る）。
- 指摘が 10 件を超えていないか（超えていたら重要度で切る。残りは「その他の気づき」として箇条書きで末尾に）。
